# Incident: product truth-lock byte-store desync ("cutout hilang bila update")

Status: fix landed (operator unblock + containment); **durable cure is owner-gated**
(see §5). Recorded 2026-08-19.

## Symptom (operator-visible)

- Manual / Canva card shows the cutout as **"Not available"** even when it is marked
  ✓ OFFICIAL / CURRENT SYSTEM REFERENCE.
- Clicking **REPLACE MANUAL CUTOUT** returns
  `API 409 {"code":"TRUTH_LOCK_HISTORY_REQUIRED","message":"The previous truth-lock
  bytes are unavailable; replacement is blocked to preserve audit history."}`.
- Recurs after "system updates" / module redeploys — the classic *"dah save hilang
  bila update"* complaint. It affected **all locked products**, not one.

## Root cause (two layers)

**Layer 1 — the runtime byte store is empty for the promoted DB.**
The live agent reads `BASE_DIR/data/exact-product/product-<sha256(id)[:24]>/…` and the
`product_visual_truth_lock` DB row's `canonical_source_path` / `canonical_cutout_path`.
A scan of the live `flow_agent.db` found **310 truth-lock rows, 0 with their canonical
bytes present** — every row's source AND cutout files were missing from the store. So
`_archive_existing_truth_lock` (in `agent/services/product_truth_lock_service.py`) could
not archive the prior cutout before replacing it, the recovery paths found no matching
bytes, and the guard fail-closed with the 409. Fail-closed was doing its job over a
store whose files had vanished — not a logic regression in the feature.

**Layer 2 — why the bytes vanish, and keep vanishing.**
`flow_agent.db` is gitignored, so it is promoted to the canonical repo root and
survives. The byte store under `data/exact-product/` is **untracked and (was) not
gitignored**, and cutout generation historically ran inside **disposable worktrees**
(e.g. `.claude/worktrees/product-cutout-bind-automation-20260808`, which still held 892
cutout + 906 source files). Each cycle — *generate-in-worktree → promote DB to root →
discard/prune worktree* — leaves the DB pointing at byte files that only existed in the
now-gone worktree. `git clean -fd` on the untracked store finishes the job. DB survives,
bytes don't, every update.

Recoverability from the stranded worktree at diagnosis time: **sources 281/310 match the
DB SHA, cutouts 0/310** (cutouts were regenerated by the 1000px-canvas standardization
*after* that worktree's snapshot, and those newer bytes are gone).

## Fixes landed (this change)

1. **Tombstone-degrade the archive guard** (`_archive_existing_truth_lock`). When prior
   bytes are genuinely unrecoverable (after the existing recovery attempt), record a
   **metadata-only history tombstone** — preserving the true SHAs, media ids, dimensions
   and provenance from the DB, with null byte paths and a
   `provenance.history_byte_status = "UNAVAILABLE"` marker — and let the replace proceed.
   A lost byte store can no longer permanently trap a replacement, and the audit trail's
   integrity (what was locked, when, superseded by what) is preserved in the DB. The
   tombstone never archives *wrong* bytes, so it cannot corrupt the chain.
2. **Gitignore the runtime byte store** (`.gitignore`: `data/exact-product/product-*/`,
   `data/exact-product-cutouts/`) so `git clean -fd` and branch switches stop wiping the
   live store. The tracked demo fixture `data/exact-product/MWCB_25ML_CAP_BURUNG/` is
   unaffected.
3. **Preflight detection** (`scripts/doctor-runtime-storage.py`): a read-only
   `TRUTH_LOCK_BYTES_MISSING — N/M` probe so a desync surfaces at preflight instead of
   when an operator clicks REPLACE.
4. **One-time recovery** (`scripts/repair-truth-lock-bytes-from-worktree.py`): restores
   SHA-verified bytes from a fallback root (default: the cutout worktree). Dry-run by
   default; `--apply` to write. Recovers ~281 sources; cutouts must be re-uploaded (their
   exact bytes are gone).

## What is fixed vs. still open

- **Permanent:** REPLACE is never again hard-walled by missing prior bytes; the
  git-clean wipe vector is closed; desyncs are detectable at preflight.
- **Recoverable now:** up to 281 source images via the repair script.
- **Still open (needs the §5 cure):** cutouts generated in a worktree can still be
  orphaned on the *next* promote-then-prune cycle. Operators will not be *blocked*
  (tombstone), but previews can go "Not available" until re-uploaded.

## 5. Durable cure (OWNER-GATED — not done in this change)

The byte store must live **outside** the git checkout and outside disposable worktrees,
co-located with the DB in one stable location shared by every checkout/worktree. The
intent is already stated in `scripts/deploy-canonical-release.ps1` ("the canonical
MUTABLE DB stays external") but violated by `scripts/start-canonical-runtime.ps1`, which
pins `FLOW_AGENT_DIR = $Repo` (the mutable dev checkout).

Recommended: point `FLOW_AGENT_DIR` at a dedicated external root (e.g.
`C:\Users\USER\Desktop\_bosmax_runtime\data`) in `start-canonical-runtime.ps1` **and**
in every worktree used for visual-pipeline work, then migrate the current
`flow_agent.db` + `data/` there once. This is owner-gated because mis-pointing the
runtime at an empty root is an immediate empty-store outage; it must be staged and
verified (run `scripts/doctor-runtime-storage.py` after the move).
